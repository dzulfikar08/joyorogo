# This is NOT the Turborepo you know

Turborepo configuration, task behavior, and CLI commands can vary between installed versions and may differ from your training data. Resolve the `turbo` package from this file's directory or relevant workspace; in monorepos, it may not be visible from the repository root. For example, run `node -p "require.resolve('turbo/package.json')"` from a workspace that depends on `turbo`.

Read `docs/README.md` inside that installed package first, then read the relevant pages from its `docs/` directory before changing Turborepo configuration or commands. Heed deprecation notices. These bundled docs match the installed package version and are available without network access.

This block is written and re-added by `turbo` before repository-scoped commands when an AI agent is detected. In the Turborepo source repository, its template is defined in `crates/turborepo-cli/src/cli/agent_guidance.rs`. Removing the managed block while updates are enabled means a later qualifying invocation will add it again. Set `"agentGuidance": false` in the root `turbo.json` or `turbo.jsonc` to opt out; this does not remove an existing block. Keep the block committed with your work to avoid an uncommitted change on the next agent invocation.

## Typechecking uses tsrs, not tsc

`check-types`, `postinstall` and CI run `tsrs` (pinned exact in the root `package.json`; Rust port of the TypeScript 7 checker): `tsrs --noEmit` to check, `tsrs -b` for the project-reference packages (api, auth, db, i18n) that write `.d.ts` to `dist/`. Never run bare `tsrs` or `tsrs -p .` in an app: without `--noEmit` it emits JS. `tsc` stays installed only for vite/tsdown/editors and for `--init`/`--showConfig`, which tsrs does not support.

Other packages read API types from `packages/api/dist`, which is generated and gitignored. If an app reports stale or missing `@joyorogo/api` types after you changed api, db, auth or i18n, run `bunx tsrs -b packages/api` (or `bun run dev:types`). `routeTree.gen.ts` in apps/web and apps/fit is generated by the vite build, so run it before typechecking those apps.

## Marketing: every user-visible feature gets a release entry

When your change adds or visibly changes something a user can see or use (screen, feature, setting, supported device,
plan or price, a fix people asked for in public), finish with both steps below. Skip refactors, tests, CI, internal
tooling, docs-only and invisible fixes.

1. Write `docs/marketing/releases/YYYY-MM-DD-<slug>.md` from the template in `docs/marketing/releases/README.md`, one
   file per feature. If the feature already has an entry, update that file (for example `available: code` to
   `test-build`) instead of adding another.
2. Create an atur issue (workspace `joyodigitama`, project Joyorogo `JRG`) titled `[Konten] JoyoRogo: <feature>`, state
   Todo, as a sub-issue of JRG-235 (`parent_id` `62fc3334-ca8a-4427-b236-ce1c50b2bc52`), with the entry's angle and
   path, and put its key in the entry's `atur:` field. If atur is unreachable, leave `atur:` empty; the weekly sweep
   files it.

Claims follow `docs/marketing/marketing-plan.md` section 1.1 and `docs/marketing/social-playbook.md`. Never call a
feature available in the Play Store or App Store before it is.

## D1 limits: bounded statements, tests on the guarded database

Cloudflare D1 refuses more than 100 bound parameters per statement (also 100 KB of SQL, 2 MB per value, 50-byte LIKE patterns); local SQLite allows 32766, so a query sized by the caller passes every test and 500s in production. Tests get their database from `d1TestDb()` in `@joyorogo/db/test-d1` (never `createClient`), which throws what D1 throws; caller-sized work goes through `packages/api/src/lib/d1.ts` (`insertChunked`, `readChunked`, `chunk`). Details: `docs/d1-limits.md`.
