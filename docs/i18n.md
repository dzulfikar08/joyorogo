# Internationalisation (i18n)

JoyoRogo ships in Indonesian (`id`, the source language and default), English (`en`) and Bahasa Melayu as written in Malaysia (`ms`, machine-drafted, see "Bahasa Melayu" below).
Web (`apps/web`), native (`apps/native`) and the API (`packages/api`, `apps/server`) share one
translation package, `packages/i18n` (`@joyorogo/i18n`), built on **i18next**
(+ **react-i18next** in each app).

## Layout

```
packages/i18n/src/
  locale.ts        LOCALES, Locale, resolveLocale(), matchLocale(), LOCALE_HEADER
  resources.ts     imports every JSON file; `id` is the source of the key types
  core.ts          i18n (client instance), initI18n(), getT(locale, ns) (server/format helper)
  format.ts        Intl-based formatters (numbers, Rp, kcal, dates, relative days)
  keys.ts          missingKeys()/orphanKeys(): used by tests and `bun run i18n:check`
  types.ts         typed keys (module augmentation of i18next)
  locales/<locale>/<namespace>.json
apps/web/src/lib/i18n.ts            browser init + setLocale()
apps/web/src/components/locale-sync.tsx
apps/native/src/lib/i18n.ts         device init + setLocale() (SecureStore)
apps/native/components/locale-sync.tsx
packages/api/src/lib/messages.ts    serverT(locale, ns), userLocale(db, userId)
packages/api/src/lib/ai-locale.ts   output-language rules for AI prompts
```

`react-i18next` is deliberately **not** a dependency of `packages/i18n`: web and native use
different React versions and the binding must resolve the app's own copy. Each app passes
`initReactI18next` to `initI18n()`.

## Which language is used

First match wins, on both clients:

1. the account's saved choice (`profile.locale`, set with `orpc.profile.setLocale`),
2. the choice stored on this device (`localStorage["jrg-locale"]` / SecureStore `joyorogo.locale`), so it works before login,
3. the browser/device language (`en-US` → `en`, `ms-MY` → `ms`; anything unshipped is skipped). Only when no listed language is shipped does the region count: a Malaysian region (`zh-MY`, `ta-MY`) gives `ms`. `en-MY` stays `en`, and `["zh-MY", "en"]` is `en`,
4. `id`.

Only an explicit pick is stored, so people who never chose follow their device. `LocaleSync`
applies the account choice after login and uploads a pre-login device choice when the account
has none. Every API request carries `x-locale` (the language the UI shows); the server puts it
on `context.locale` (falls back to `id`: pre-i18n app builds send no `x-locale` and only render Indonesian). Background work (push, cron
email) has no request: read the recipient's saved language with `userLocale(db, userId)`.

Switching language remounts screens (web: the root route tree; native: stack screens via
`screenLayout`, and the tab screens) so values formatted by the shared helpers refresh.

## Namespaces

One JSON file per namespace per language, named after the feature as the code names it:

| namespace    | holds                                                              |
| ------------ | ------------------------------------------------------------------ |
| `common`     | shared actions, states, dates/times, meal & activity labels, nav, error screen |
| `makan`      | food log: diary, scan/story/barcode flows, favourites, plate       |
| `olahraga`   | exercise and workouts (`latihan`)                                  |
| `tidur`      | sleep                                                              |
| `berat`      | weight and waist                                                   |
| `maternal`   | Hamil and Menyusui: setup form, targets, nutrients, weight gain, food-safety flags, disclaimer (see `docs/maternal-mode.md`) |
| `gain`       | Naikin BB (weight gain): goal chooser, surplus plan, "Kurang X kkal lagi" states, target-date verdicts, safety notes, recap and reminder copy (see `docs/gain-mode.md`) |
| `auth`       | login, onboarding                                                  |
| `billing`    | Pro, pricing, checkout                                             |
| `settings`   | profile/settings (`profil`), language, reminders, privacy          |
| `errors`     | **server** user-facing API errors                                  |
| `push`       | **server** push notification text                                  |
| `email`      | **server** email text                                              |

Not every namespace exists yet: create `locales/{id,en}/<ns>.json` and register it in
`resources.ts` (import both, add to `id` and `en`) with the first screen that needs it.
Anything used by 3+ screens of different namespaces moves to `common`.

## Key naming

- camelCase segments joined by dots, 2-4 levels: `area.element.state`. Name the **role**, not the
  words: `list.empty.title`, `sheet.move.hint`, `toast.deleted`. Never use the Indonesian text as the key.
- Group by screen area first (`summary.*`, `list.*`, `sheet.*`, `toast.*`, `error.*`), not by component file.
- Actions that mean the same thing everywhere (`Simpan`, `Batal`, `Hapus`) live in `common:actions.*`.
  Reuse them; do not copy "Simpan" into every namespace.
- Segments never contain `.` or `:` (they are the path and namespace separators): `fasting.hint.window` with
  `{{fast}}`/`{{eat}}` params, not a key named `16:8`.
- Enum values stored in the database (`sarapan`, `makan_siang`, `low`) keep their value as the
  last key segment: `common:meal.label.makan_siang`.
- Typed keys: `useTranslation("makan")` then `t("summary.title")`. To reach another namespace from the
  same `t`, list it too: `useTranslation(["makan", "common"])`, then `t("common:actions.save")`
  (react-i18next only types a prefix for namespaces named in the hook). tsrs fails on a key missing from `locales/id`, and on a key that
  `en` lacks (English is typed as `typeof id`).

## Add a string

1. Add the key to `locales/id/<ns>.json` (the Indonesian text as it is today) **and** `locales/en/<ns>.json`.
2. Use it:

   ```tsx
   const { t } = useTranslation(["makan", "common"]); // first = default namespace
   <Text>{t("list.empty.title")}</Text>
   <Button>{t("common:actions.save")}</Button>
   ```

   Outside components (stores, mutations' `onSuccess`, plain functions) use the shared instance:
   `import { i18n } from "@joyorogo/i18n"; i18n.t("makan:toast.deleted")`.
3. Module-level constants must not hold translated text: they run once, in the first
   language. Make them functions, or arrays of keys translated at render.
   (Label tables like `MEAL_LABELS` are lazy getters for this reason.)
4. `bun run i18n:check` and `bun run check-types` (web, native, api) must pass.

## Add a language

1. Add the code to `LOCALES` and a name to `LOCALE_NAMES` in `locale.ts`; `INTL_TAG` in `format.ts` (and `LANGUAGE_NAME` in `packages/api/src/lib/ai-locale.ts`).
2. Copy `locales/id/*.json` to `locales/<code>/` and translate. Use `en` as a style reference, not as the text to translate when you can read `id`.
3. Register the files in `resources.ts`. tsrs and `i18n:check` list everything missing.
4. Plural categories differ per language (e.g. Arabic has six). Add a `_zero|_one|_two|_few|_many|_other` form for each category `Intl.PluralRules(<code>).resolvedOptions().pluralCategories` reports; `i18n:check` enforces it.
5. The language picker (Settings) lists `LOCALES`, nothing else to wire. Add the date/number checks to `format.test.ts`.

## Bahasa Melayu (`ms`)

Written for Malaysian readers, not as Indonesian with swapped words: `kalori`, `makan tengah hari`, `hidangan` (portion), `imbas` (scan), `kumpulan` (group), `kawan`, `percuma`, `anda`, `RM`. The glossary and the Indonesian-only word list live in `packages/i18n/src/ms-malay.test.ts`, which fails when a string contains a word that exists only in Indonesian (`kamu`, `bisa`, `olahraga`, `kkal`, ...). `ms` uses `kcal` (Malaysian labels print kcal), `ms-MY` number and date formats (`1,234.5`, `Isnin, 14 September 2026`) and `fmtMyr` for ringgit.

- Plural: Malay has only the `other` category, so `ms` copies the `id` key set. A leftover `_one` copied from the source is tolerated (`orphanKeys` ignores plural forms whose base key is required); do not add new ones.
- Detection: `matchLocale` maps `ms`, `zsm`, `msa`, `may` (any region: `ms-MY`, `ms-BN`) to `ms`; `matchRegionLocale`/`matchTags` give the Malaysian region fallback described above.
- Region is separate from language: `resolveRegion({ locale, country })` (`packages/i18n/src/region.ts`) says `MY` for a `ms` UI or `CF-IPCountry: MY`, `SG` for `CF-IPCountry: SG` (Singapore has no language of its own: an English UI there is `SG`, a `ms` UI is still `MY`), else `ID`. The API puts it on `context.region`; it picks the nutrient table (`lib/tkpi.ts` `indexFor`: `MY` and `SG` both read the HPB SG FoodID table first) and the dish defaults of the scan prompts (`lib/region-prompt.ts`). Clients get it from `region` in `/api/config` (`setActiveRegion`), which picks the equivalence line ("Same as N plates of chicken rice" in Singapore) and the loading-screen facts. See `docs/marketing/malaysia-plan.md`.
- Day zone: a day is cut in the person's zone (`profile.timezone`: Asia/Jakarta, Asia/Kuala_Lumpur, Asia/Singapore; a profile without one is Jakarta). `packages/i18n/src/day-zone.ts`: apps set `setActiveDayZone` and every zone-less helper follows it; the server passes `await userZone(context)` explicitly (plan, "Timezone").
- Not yet Malay: the public site pages (landing, `/harga`, `/privasi`, `/syarat`, blog) are Indonesian only except `/my`; AI prompts stay Indonesian with `localName` in Malay; recipe and meal-plan data in `meal/` stays Indonesian.

## Plurals

Use a `count` option and the i18next suffixes. Indonesian has one form, `_other`; English has
`_one` and `_other`.

```json
// id/makan.json                              // en/makan.json
"items_other": "{{count}} makanan"            "items_one": "{{count}} item",
                                              "items_other": "{{count}} items"
```

```ts
t("summary.items", { count: foods.length }); // note: key without the suffix
```

Format big numbers yourself and pass them as a separate param (`{{kcal}}`), keeping `count` for the
plural decision: `t("x", { count: n, kcal: fmtInt(kcal) })`.

## Interpolation

`{{name}}` placeholders; values are plain strings/numbers. Never build a sentence by concatenating
translated fragments: word order differs per language, so the whole sentence is one key.

```json
"sheet.move.hint": "Akan dipindah ke {{date}}."   //  "Will be moved to {{date}}."
```

No HTML in strings. For markup inside a sentence use `<Trans>`:

```tsx
<Trans ns="makan" i18nKey="plan.eatBudget" values={{ kcal }} components={{ b: <b /> }} />
// "plan.eatBudget": "Sisa <b>{{kcal}}</b> kcal"
```

(React Native: pass `<Text style={bold}/>` as the component.) `escapeValue` is off because React escapes.

## Formatting helpers (`@joyorogo/i18n`)

Never hand-format with `toLocaleString("id-ID")` or hard-coded "Rp"/"kcal"/"Hari ini". All helpers
take an optional last `locale`; clients omit it (the active language), **server code must pass it**.

| helper                              | id                    | en                      |
| ----------------------------------- | --------------------- | ----------------------- |
| `fmtInt(1234.6)`                    | `1.235`               | `1,235`                 |
| `fmtNumber(2.5, 1)` / `fmtDecimal(2.5, 2)` | `2,5` / `2,50`  | `2.5` / `2.50`          |
| `fmtKg(68.46)`                      | `68,5`                | `68.5`                  |
| `fmtIdr(15000)`                     | `Rp15.000`            | `Rp15,000`              |
| `fmtKcalLabel(2100)` / `fmtGramsLabel(120)` | `2.100 kcal` / `120 g` | `2,100 kcal` / `120 g` |
| `fmtPercent(42)`, `fmtRatio(0.53)`  | `42%`, `0,53`         | `42%`, `0.53`           |
| `fmtDate("2026-09-14", "long")`     | `Senin, 14 September 2026` | `Monday, September 14, 2026` |
| `fmtDateMedium` / `fmtDateShort`    | `14 Sep 2026` / `14 Sep` | `Sep 14, 2026` / `Sep 14` |
| `relativeDayLabel(date, today)`     | `Hari ini` / `Kemarin` / `Sabtu, 10 Okt` | `Today` / `Yesterday` / `Saturday, Oct 10` |
| `timeAgo(date)`                     | `5 menit lalu`        | `5 minutes ago`         |
| `fmtClock(date)` (day zone)         | `13.05`               | `01:05 PM`              |
| `mealLabel(meal)` (engine)          | `Makan Siang`         | `Lunch`                 |
| `shortDayLabel` / `recentDayLabel` / `monthLabel` (`@joyorogo/api/lib/format`, no Intl) | `Sen, 5 Okt` / `Hari ini` / `Okt 2026` | `Mon, Oct 5` / `Today` / `Oct 2026` |

Label tables that screens index by key (`MEAL_LABELS`, `ACTIVITY_LABELS`, `FOOD_KIND_LABELS`,
`MAKAN_VIEWS[].label`, ...) are lazy getters built with `localizedLabels()` (`lib/engine.ts`): they
follow the active language, so call sites stay unchanged. Server code must not read them: use
`mealLabel(meal, locale)` and the other functions with a `locale` parameter.

`fmtDate` styles: `short`, `medium`, `long`, `weekday`, `month`. Calendar days ('YYYY-MM-DD',
WIB) are formatted in UTC so they never shift. `relativeDayLabel` and the meal/activity label
tables are re-exported from `@joyorogo/api/lib/engine` for existing call sites.

The app-level `format.ts` files (`apps/web/src/lib/format.ts`, `apps/native/utils/format.ts`) now
re-export these; `fmtDateIndo` → `fmtDateLong`, `fmtDateId` → `fmtDateMedium`.

## Server text

- **API errors**: `serverT(context.locale, "errors")("profile.onboardingRequired")` inside the handler.
- **Push**: write to the recipient's language: `pushFeed(ctx, toUserId, (t) => ({ title: t("social.kudos", { name }) }))`; cron/background code uses `userLocale(db, userId)`.
- **Email**: `getT(locale, "email")`; the admin payment notice stays Indonesian (internal).
- **AI prompts**: `analyzeFoodPhoto(ai, { …, locale })` and `parseFoodStory(ai, { …, locale })`. The
  prompts stay Indonesian (TKPI data and local dishes are Indonesian); for other locales the model
  also returns `localName`, and the parser keeps `name` (Indonesian, used for TKPI matching, broth
  and food-kind detection) until the end, then swaps `localName` in. `transcribeStory` takes the
  Whisper language. See `ai-locale.ts`.
- Never keep a module-level "current language" on the server: a Worker serves all languages at once.
- **Scan failures**: the server throws `ORPCError` with the localized message (`scanFailMessage(reason, locale)`,
  `lib/scan-fail-message.ts`) and `data: { reason }`, one of `SCAN_FAIL_REASONS`. Clients read the code with
  `scanFailReason(error)` (`lib/scan-errors.ts`, duck-typed) and show `scan:fail.reason.<code>.title|message`;
  nothing matches on message text. `VisionError.message` is a log string (`scan:<reason>`). The anonymous landing
  scan (`apps/server/src/anon.ts`) answers `{ error, reason }` in the request language (`requestLocale`).
  Barcode `incomplete` results carry a `reason` code (`no_kcal`, `implausible`), not text.
- **VAR perut**: the prompt stays Indonesian; failures and `ORPCError`s are localized through `varperut:errors.*`
  (`locale` is passed into `analyzeVarPhotos`, `retryVarScan`, `restoreVarVerdict`). Server-only strings live under a
  top-level `errors` group in `scan`/`barcode`/`varperut`.
- Not yet migrated: most other `ORPCError` messages (grep `ORPCError(` in `packages/api/src`), group nudge push
  text, `tips`/`ideas`/`challenge`/`place` text libs.
  `bun run i18n:check --list` covers the apps; for the API, grep for Indonesian in `packages/api/src`.

## What is never translated

- Brand and product names: JoyoRogo, JoyoFit, Pro, Founder (plan names), Strava, Google, Apple.
- Food names from data: TKPI table/dish names, saved foods, anything the user or the AI named.
  The food *database* stays Indonesian; AI scan output for non-`id` users is `localName`.
- User-written content (posts, comments, notes, names), handles, invite codes.
- Units: `kcal`, `g`, `kg`, `cm`, `ml`. Currency: `Rp`.
- Language names (`LOCALE_NAMES`): each language in its own language.
- Route paths (`/makan`, `/profil`), query keys, analytics events, database enum values.
- Log/diagnostic messages (`console.error`).

## Checking

```
bun run i18n:check
```

1. lists keys `id` has that `en` lacks (plural-aware) and `en` keys with no `id` source; exits 1 on either,
2. reports files under `apps/web/src` and `apps/native` (app, components, src, utils, lib) that still contain
   Indonesian UI literals — JSX text, and string props such as `title`, `label`, `placeholder`,
   `description`, `message`, `aria-label`, `accessibilityLabel` — with a count per app and per file.
   This one is a regex heuristic over a word list (`scripts/i18n-check.ts`): it can miss a literal and rarely
   flags a false positive. It informs the migration; it does not fail the build.

`packages/i18n/src/keys.test.ts` fails `bun test` when `en` is incomplete.

## Checklist: migrating a screen

1. Pick the namespace (add one if the screen is the first of its area). Read the keys that already exist: reuse before adding.
2. Replace every UI literal: JSX text, `title`/`label`/`placeholder`/`description`/`aria-label`/`accessibilityLabel`, toast and alert messages, `document.title`/head titles, empty states, validation messages.
3. Turn every `count + noun` into a plural key; every sentence with a value into one interpolated key.
4. Replace hand-rolled number/date/currency formatting with the helpers above; delete the local copy.
5. Module-level label tables → lazy (function, getter, or keys translated at render).
6. Strings that come from the server: `ORPCError` text is localized there (`context.locale`); text computed in `packages/api/src/lib` and displayed by the client (e.g. `snack-advice`) goes through `@joyorogo/i18n` with the active language.
7. Write the `en` text: natural, plain, short; not a literal translation. Keep the tone (friendly, "kamu" → "you").
8. Leave brand names, food names and units alone.
9. `bun run i18n:check`: the screen's files must drop out of the literal list; `bun run check-types` in the app; `bun test`.
10. Switch language in Settings and look at the screen in both languages (long English strings must not clip).
